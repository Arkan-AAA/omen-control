# Дизайн: OMEN Control (рабочее название) — переписывание OMEN Gaming Hub на Rust

Дата: 2026-11-12
Статус: черновик, ожидает одобрения

## Намерение и почему

Создать открытый нативный Rust-аналог HP OMEN Gaming Hub, ориентированный на
**управление железом** ноутбуков HP OMEN / HyperX: профили производительности,
RGB-подсветка, управление вентиляторами, системные показатели, сетевой бустер.
Целевая аудитория — переходящие на Linux (особенно Arch/CachyOS), которым
нужен OMEN-подобный контроль, а также пользователи Windows, которым нужен
более лёгкий и быстрый клиент. HP-аккаунт, облако, обновления прошивки,
игровая библиотека и стриминг вне рамок (только hardware parity).

Вдохновение: ArtCraft — чистый Rust, нативно (без web-обёрток), open source,
всё локально.

## Цели

- Нативное Rust-десктоп-приложение, кроссплатформенное: **сначала Windows, затем Linux (Arch/CachyOS)**.
- Hardware parity для: Performance Control, Lighting/RGB, Fan Control, System Vitals,
  Network Booster (best-effort), настройки производительности.
- Стильный современный UI (Slint), игровая эстетика, тёмная тема по умолчанию.
- Модульная абстракция устройств: новые модели OMEN/HyperX добавляются без
  переписывания приложения.
- Открытый код на GitHub, воспроизводимые сборки и релизные артефакты.

## Не цели

- HP-аккаунт / облачные сервисы / телеметрия.
- Обновления прошивки / BIOS.
- Игровая библиотека, лаунчер, стриминг (Oasis).
- Поддержка macOS (не запрашивалась; архитектура может позволить позже).
- Десктопные OMEN в v1 (сначала ноутбуки).

## Анти-цели (что сделало бы проект неудачным, даже если «работает»)

- Требование запускать всё приложение от root/admin для обычного использования.
- Повреждение или дестабилизация железа невалидированными записями в EC/ACPI.
- Жёсткая привязка к протоколу одной модели, из-за которой вторую модель
  придётся переписывать.
- Поставка web view / Electron-подобной обёртки (должно остаться чисто нативным).

## Ограничения

- На Linux нет официальных драйверов/API HP; придётся опираться на community
  reverse engineering (omen-rgb, hp-omen-linux, nbfc, ryzenadj, lm-sensors,
  hidraw, sysfs, ACPI/EC).
- Сторона Windows может использовать WMI (HpWmi), HID, NVML, но часть вызовов
  тоже требует реверс-инжиниринга.
- Привилегированный доступ к железу должен быть изолирован (polkit helper на
  Linux, elevated helper service на Windows), чтобы UI работал без привилегий.
- Не нарушать EULA HP так, чтобы это блокировало личное использование /
  опенсорс нашего кода; поставляем только свой Rust-код, никогда бинарники HP.

## Рассмотренные подходы

1. **Полный клон с нуля** (все протоколы реверсятся, всё нативно).
   - Плюсы: максимальный контроль, без внешних зависимостей.
   - Минусы: годы работы, высокий риск повреждения железа, блокирует релиз.
   - Вердикт: отклонён как основной; поглощается инкрементально.

2. **Linux-first обёртка над community-утилитами + Rust GUI** (вызов omen-rgb,
   nbfc, ryzenadj как подпроцессы).
   - Плюсы: быстрый MVP, использует известные рабочие протоколы.
   - Минусы: хрупкий UX, накладные расходы процессов, плохая диагностика.
   - Вердикт: используется как *тактика* для Linux позже, за чистым trait.

3. **Кросс-платформенный core + нативные платформенные backend'ы + Slint UI** (рекомендуется).
   - Плюсы: тестируемый core, общий UI, Windows и Linux равноправны,
     модели добавляются как данные + небольшие backend-реализации.
   - Минусы: больше проектирования заранее, два backend'а на поддержку.
   - Вердикт: **выбран**.

## Выбранный подход

Подход 3, с Windows-first поставкой: сначала строим и валидируем Windows-backend,
Linux-backend остаётся за тем же trait для фазы 3.

## Архитектура

Cargo workspace:

```
omen-control/
  crates/
    omen-core/          # traits, types, errors, device model, config
    omen-platform/      # cfg-gated re-exports платформенных backend'ов
    omen-windows/       # Windows backend (WMI, HID, NVML)  [FIRST]
    omen-linux/         # Linux backend (hidraw, sysfs, polkit helper client)
    omen-ui/            # Slint app, экраны, темы
    omen-helper/        # привилегированный helper-бинарник (Windows service / Linux polkit)
  packaging/            # Windows installer, PKGBUILD, .deb/.rpm
  docs/
```

Ключевой trait (в `omen-core`):

```rust
pub trait OmenDevice: Send + Sync {
    fn info(&self) -> DeviceInfo;
    fn vitals(&self) -> Result<Vitals>;
    fn performance_modes(&self) -> &[PerformanceMode];
    fn set_performance_mode(&self, mode: PerformanceMode) -> Result<()>;
    fn fan_curve(&self) -> Result<FanCurve>;
    fn set_fan_curve(&self, curve: FanCurve) -> Result<()>;
    fn rgb_zones(&self) -> Vec<RgbZone>;
    fn set_rgb(&self, zone: RgbZoneId, color: Rgb) -> Result<()>;
    fn network_stats(&self) -> Result<NetworkStats>;
}
```

Backend'ы реализуют trait для каждого семейства моделей. Детекция модели при
старте через SMBIOS (Windows: WMI `Win32_ComputerSystem`/`Win32_BaseBoard`,
Linux: `/sys/class/dmi/id/*`).

## UI (Slint)

Экраны:
- Dashboard (обзор показателей, текущий режим, быстрые переключатели)
- Performance (выбор режима, лимиты мощности CPU/GPU, редактор кривой вентиляторов)
- Lighting (RGB по зонам, эффекты, яркость)
- Fans (редактор кривой с графиком, ручной override)
- System Vitals (подробные сенсоры, график истории)
- Network (пропускная способность, по процессам, базовая приоритизация)
- Settings (автозапуск, тема, проверка обновлений)

Темы: тёмная игровая, акцентный цвет настраивается, компактный layout для
экранов ноутбуков.

## Модель привилегий

- UI-процесс работает от обычного пользователя.
- Привилегированные операции идут через `omen-helper`, отдельный бинарник:
  - Windows (сначала): служба Windows от SYSTEM с named pipe; UI подключается
    и шлёт типизированные запросы.
  - Linux (позже): polkit-действие `com.omencontrol.helper`, helper вызывается
    через D-Bus или pkexec; валидирует и разрешает команды.
- Helper раскрывает только типизированные валидированные операции (смена
  режима, запись кривой вентиляторов, RGB-пакет) — никогда произвольный
  shell/root.

## Данные и конфиг

- Пользовательский конфиг: TOML в OS config dir (`~/.config/omen-control/` / `%APPDATA%`).
- Профили: именованные пресеты производительности/вентиляторов/RGB,
  экспорт/импорт.
- Логи: tracing в файл + stderr, ротация.

## Платформенные особенности

Windows (сначала):
- WMI для системной информации и HP-специфичных классов, NVML для NVIDIA, HID для RGB.
- Пакетирование: MSI или portable zip через cargo-wix/nsis, GitHub Actions.

Linux (CachyOS/Arch, позже):
- DMI-детекция, hwmon для температур/вентиляторов, hidraw для RGB,
  ryzenadj/ectool для питания (через helper), tc/nftables для сетевой
  приоритизации (best-effort).
- Пакетирование: PKGBUILD (AUR), плюс .deb/.rpm для Ubuntu/Fedora.
- Зависимости: lm-sensors, ryzenadj, (опционально) nbfc.

## Стратегия тестирования

- Unit-тесты в `omen-core` для типов, конфига, парсинга, математики кривой вентиляторов.
- Mock-реализация устройства для разработки UI без железа.
- Hardware-in-the-loop: ручной чеклист на семейство моделей, документируется в
  `docs/hardware-testing.md`.
- CI: cargo fmt, clippy, тесты на Windows (и Linux позже); сборка релизных артефактов.

## Фазы поставки (сначала Windows)

Phase 0 — Скаффолд репозитория, CI, Slint hello-world, mock-устройство (1-2 недели)
Phase 1 — Windows: показатели + переключение режимов производительности (2-4 недели)
Phase 2 — Windows: управление вентиляторами + RGB на модели пользователя (3-6 недель)
Phase 3 — Linux (CachyOS/Arch): parity backend (3-6 недель)
Phase 4 — Сетевой бустер, профили, полировка, пакетирование, документация (2-4 недели)
Phase 5 — Дополнительные модели (сообщество)

## Что остаётся на усмотрение строителя (детали реализации)

- Точные форматы HID-пакетов на модель (нужен реверс; начинать с машины
  пользователя и community-проектов).
- Интерполяция кривой вентиляторов и safety-ограничения.
- ryzenadj vs прямые MSR-записи (фаза Linux).
- Объём сетевого бустера (только мониторинг vs QoS) — рекомендуется
  мониторинг + простая приоритизация по процессам.
- Конкретная библиотека компонентов Slint / набор иконок.
